# Prompt Radar — аналитика AI-агентов и ROI

Готовый, воспроизводимый проект для ответа на вопрос CTO: **какие сценарии решают агенты, какими инструментами они пользуются и окупается ли платформа**.

Он анализирует JSON-логи диалогов, строит сценарии использования и создаёт самостоятельный HTML-отчёт с TCO, стоимостью токена, экономией времени и ROI по каждому агенту.

## Быстрый старт

Нужен только Python 3.10+.

```bash
python main.py
python -m unittest discover -s tests -v
```

Результаты появляются в `outputs/`:

- `report.html` — отчёт для руководителя;
- `analytics.csv` — строка на диалог с токенами, инструментами и экономикой;
- `use_cases.csv` — сценарии, категории, примеры и ошибки;
- `agents_roi.csv` — сравнение A, B и ROI по агентам;
- `economics.json` — финальные компоненты TCO и unit economics;
- `data_quality.json` — невалидные файлы и происхождение классификации.

Для своего набора данных:

```bash
python main.py --dialogs-dir /path/to/logs --outputs-dir /path/to/output \
  --economics-config config/economics.json
```

## Что именно считает проект

### A: затраты

`config/economics.json` содержит все допущения, поэтому их можно защитить перед финансовым директором:

```text
TCO за месяц = CAPEX сервера / срок амортизации / 12
              + мощность (кВт) × 730.5 × загрузка × тариф электроэнергии
              + команда продукта и инференса
              + лицензии × active user-months

стоимость токена = TCO за период / токены за период
```

В примере используются ваши стартовые вводные: сервер `100 млн ₽`, пять лет амортизации (то есть `20 млн ₽` в год), тариф и мощность заданы отдельными параметрами. Поле `monthly_token_capacity` нужно заполнять измеренной производительностью сервера в месяц: тогда стоимость токена не будет зависеть от размера экспортированной выборки.

Команду разработки и инженеров **нужно добавлять** при обосновании инвестиции в продукт (полный TCO). Для сравнения производительности самого железа показывайте её отдельной строкой, иначе смешиваются две разные управленческие метрики. В конфиге это `monthly_product_and_inference_team_rub`.

Лицензия платного агента также задана отдельно (`10 000 ₽` за active user-month). Её можно поставить в ноль, если сценарий — только self-hosted инференс; так не возникнет двойного учёта.

### B: эффект

```text
стоимость минуты FTE = 400 000 ₽ / (22 дня × 8 часов × 60 минут)
B = сумма(минуты, сэкономленные сценарием) × стоимость минуты FTE × коэффициент реализации
ROI = (B − A) / A
```

По умолчанию сценариям назначены консервативные минуты; меняйте их в `minutes_by_category` после замеров. `value_realisation_rate = 0.7` означает, что в деньги превращается только 70% теоретически сэкономленного времени. Поэтому вывод `B > A` в отчёте — прозрачная модель, а не необоснованное заявление о фактической выгоде.

Пример: если у агента за 3 месяца 100 млн токенов, его A равно `100 000 000 × cost_per_token_rub` из `outputs/economics.json`; его B и ROI уже находятся в `outputs/agents_roi.csv`.

## Логи и классификация

Поддерживается формат `session_*.json` исходного датасета: `user_id`, `agent_id`, `department`, `created_at`, `scenario_type`, `scenario`, `messages`. Инструменты считываются из сообщений с `role=tool`, например `gmail.search`, `crm.get`, `browser.search`.

В демо-датасете уже есть `scenario_type` и `scenario`. Проект честно использует их как source labels, а не выдаёт эти метки за результат LLM. На неразмеченных логах применяется компактный keyword fallback и в колонке `classification_source` фиксируется `heuristic`.

Для production-качества классификации замените fallback на корпоративный embedding/LLM-классификатор и добавьте ручную валидационную выборку с precision/recall по категориям. Старый GPU-прототип сохранён в репозитории как справочный эксперимент; его зависимости перечислены в `requirements-ml.txt`, но он не является основным pipeline.

## Проверка данных перед решением

1. Передавайте фактические `input_tokens`, `output_tokens`, `cached_tokens` и токены tools из биллинга модели вместо оценки `chars / 4`.
2. Замените мощность сервера, загрузку, тариф и производительность на фактические метрики кластера.
3. Подтвердите минуты экономии на выборке задач «до/после» и не считайте их эффектом автоматически.
4. Отслеживайте ошибки агентов и стоимость неуспешных запусков: они остаются в `analytics.csv`.

## Известное состояние исходного репозитория

Исходный проект `lve-qw/krok-analytics` не изменялся. Его dashboard не компилировался из-за некорректной f-string, а заявленная стоимость `$0.0001 / 1k tokens` была условной и не включала амортизацию, электроэнергию, лицензии или команду. Этот репозиторий исправляет эти проблемы и запускается без загрузки моделей или GPU.
